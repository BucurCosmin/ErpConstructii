# Decizii de arhitectură

Format scurt: decizia, motivul, consecința. O decizie se schimbă doar cu o intrare nouă care o înlocuiește (nu se rescrie istoria).

| ID | Decizie | Motiv | Consecință |
|---|---|---|---|
| D-01 | **Monolit modular în .NET 10** (ASP.NET Core), un proces, module cu granițe clare. | Echipă mică; microserviciile nu se justifică la început. | Granițele de modul permit extragerea ulterioară a unui serviciu, dacă devine necesar. |
| D-02 | **PostgreSQL** (decis). | Fără licență, tranzacții solide, JSONB, RLS, colecții native. | EF Core + Npgsql; Dapper pentru rapoartele grele. |
| D-03 | **Schemă și DbContext per modul**; istoricul migrărilor în schema modulului. | Modulele evoluează independent. | Fără navigări EF între module: referințe doar prin Id. |
| D-04 | **Row-Level Security pe `firma_id`**, setat la deschiderea conexiunii (`app.firma_id`). | O greșeală în cod nu poate expune datele altei firme. | Rolul aplicației fără BYPASSRLS; migrările rulează cu alt rol. Schema `identitate` este excepție (login pe mai multe firme). |
| D-05 | **Articolul de deviz este pivotul**; versiunile de deviz aprobate sunt imuabile. | Controlul costurilor funcționează doar dacă totul se leagă de articol. | Cheie stabilă pe articol între versiuni; legăturile din alte module referă articolul. |
| D-06 | **Importatori ca module** (plugin) pentru devize, grafice, formulare: contract `IImportator<T>` + model canonic. | Formatele externe se înmulțesc; nucleul nu trebuie atins. | Un format nou = un proiect nou + o linie de înregistrare. Importatorii nu ating baza de date. |
| D-07 | **Autentificare: ASP.NET Core Identity + OpenIddict** (OAuth2/OIDC) în aplicație. Alternativa: Keycloak, dacă SSO/federarea devin necesare devreme. | Fără dependență externă la început. | Până la implementare, Host-ul pornește doar în Development (autentificare prin headere). |
| D-08 | **Fără portal pentru externi** în această etapă. | Decizia clientului. | Aprobările beneficiarului/dirigintelui se fac pe PDF semnat, atașat de managerul de proiect. Modelul de drepturi permite portalul mai târziu. |
| D-09 | **Formulare: șabloane Word ale firmei cu controale de conținut etichetate**; Open XML SDK. | Același șablon servește generării și importului exact al formularelor completate manual. | Convenția de etichete este contract cu firmele (documentată în `OpenXmlUtil`). |
| D-10 | **PDF gratuit: LibreOffice headless prin Gotenberg**, serviciu separat. | Cerință explicită: fără licențe comerciale. | Fidelitatea față de Word poate varia la șabloane complexe; se testează pe șabloanele pilotului. |
| D-11 | **e-Factura canal principal; XML UBL CIUS-RO = formatul intern al facturii.** | O singură sursă de adevăr. | PDF / export contabil sunt convertoare; integrarea ANAF stă într-un proiect separat. |
| D-12 | **Grafice: Primavera P6 și Excel primele**, MS Project la cerere; MPXJ pentru citire/scriere. | Ce folosesc firmele-țintă. | De verificat licența MPXJ (LGPL) la integrare. Excel fără dependențe → prognoză liniară. |
| D-13 | **Până în faza 3, contabilitatea rămâne în programul clientului**; exportatori contabili ca module. | Livrare mai rapidă a valorii din construcții. | Import al stării plăților din contabilitate pentru scadențar și cash-flow. |
| D-14 | **Clienți țintă: firme medii (20–250 angajați)**, arhitectură pregătită pentru firme mari. | Decizia clientului. | Multi-firmă, audit, RLS, API intern din prima zi; grupuri, workflow complex, SSO mai târziu. |
| D-15 | **Identificatorii de domeniu și comentariile în română** (fără diacritice în identificatori); termenii tehnici rămân în engleză. | Domeniul (deviz, situație, NIR) nu are traduceri fidele; codul se citește alături de documentele firmei. | Convenție în CLAUDE.md. |
| D-16 | **Sume `decimal`, rotunjire explicită „jumătate departe de zero”, cote nehardcodate.** | Devizele se verifică la ban față de programul sursă; cotele legale se schimbă. | `Rotunjire`, `ParametriRecapitulatie`; teste cu valori calculate de mână. |
| D-17 | **Frontend: React + TypeScript cu un grid serios (AG Grid)**; mobil offline-first (.NET MAUI sau React Native — de ales în faza 2). | Devizele și situațiile sunt tabele mari editabile. | Frontend-ul nu e încă început. |
| D-18 | **Interfața web: React + TypeScript + Ant Design** (Vite), în `clients/web`; **mobil: React Native** (`clients/mobile`). Înlocuiește partea de UI din D-17. | Ant Design acoperă componentele enterprise (tabele arborescente, formulare, date) fără licență; React Native refolosește tipurile, clientul API și logica din web. | AG Grid rămâne opțiune pentru editarea masivă (devize, situații), adăugat când apare nevoia. |
| D-19 | **Flux OAuth: Authorization Code + PKCE, cu pagina de login în aplicația web** (nu password grant). Login-ul creează cookie-ul Identity, `/connect/authorize` emite codul; access token 10 min, refresh token rotit; firma activă = claim `firma_id`, schimbată prin refresh token. | Password grant e interzis de OAuth 2.0 Security BCP; același flux servește aplicația mobilă (browser de sistem). | Aplicația web și API-ul trebuie servite pe aceeași origine (proxy Vite în dezvoltare, reverse proxy în producție). Emitentul se fixează în `Autentificare:Emitent`. |
| D-20 | **OCR local cu Tesseract** pentru documentele scanate (note de comandă, ulterior facturi pe hârtie); PDF randat cu PDFium. Varianta AI (viziune) a fost respinsă la acest pas. | Decizia clientului: fără costuri per pagină, documentele nu părăsesc serverul. | Calitate mai slabă pe scris de mână și scanări proaste: câmpurile neclare se marchează „de verificat” și le completează utilizatorul. Modelele de limbă (~25 MB) nu sunt în git (`scripts/descarca-tessdata.ps1`). Dependențe native: VC++ runtime pe Windows, `libtesseract5`/`libleptonica` pe Linux. Un extractor AI se poate adăuga ulterior ca alt `IExtractorText`. |
| D-21 | **Trei documente distincte în aprovizionare: necesar de materiale (NM) → notă de comandă către furnizor (NC, formularul GC 007) → factură.** Ce se numea „notă de comandă” în cod era necesarul de materiale (tabelul `note_comanda` redenumit `necesare_materiale`, tipul de formular `comanda-furnizor` → `necesar-materiale`). | Terminologia pilotului: necesarul e cererea șantierului (cu aprobare), nota de comandă e documentul trimis furnizorului. | Secvențe de numerotare separate (blocare consultativă cu sufix pe firmă). Nota de comandă e primul punct din potrivirea comandă–NIR–factură. |
| D-22 | **Dosarele scanate se clasifică pe pagini** (`ClasificarePagini`, logică pură în SharedKernel) înainte de interpretare; paginile rotite se îndreaptă automat la OCR (test pe imaginea micșorată, ±90°), iar textul recunoscut se păstrează 30 min în cache (după SHA-256). Pentru facturi, pagina e-Factura din SPV are interpretor dedicat. | Pe hârtie, factura, e-Factura, nota de comandă, avizul și certificatele stau împreună și se scanează într-un singur PDF; vizualizarea e-Factura are același format la toți furnizorii. | Interpretorii primesc doar paginile documentului lor. Cifrele izolate din celule (cantități de o cifră) scapă uneori OCR-ului: rămân „de completat”. |
| D-23 | **Stocuri: evaluare la cost mediu ponderat (CMP); recepția (NIR) confirmată de gestionar; depozite configurabile + o gestiune de șantier pe proiect.** Modul propriu (schema `stocuri`), cu drepturile Aprovizionării; citește facturile prin `IInterogareFacturiPrimite` (contract în proiectul de bază Facturi). Operațiile de stoc ale unei firme se serializează (blocare consultativă), soldurile se țin în `solduri`, mișcările în `miscari` (append-only). | Decizia clientului (de confirmat cu contabilul pilotului). Recepția separată de factură permite lipsurile la livrare. | Factura rămâne pe proiect (cost), stocul arată unde e materialul; la rapoartele de cost real se va evita dubla numărare (costul din factură vs. valoarea transferată). Anularea unei facturi deja recepționate nu anulează NIR-ul (de tratat cu stornarea NIR). |
| D-24 | **Accesul din exterior: aplicația rulează pe calculatorul firmei, expusă la `sdaq.home.ro` prin Caddy** (reverse proxy, HTTPS automat cu Let's Encrypt), pe porturile 80 / 443 redirecționate din router. Caddy servește aplicația web compilată și trimite `/api`, `/connect`, `/.well-known` la API-ul de producție (mediul Production, doar pe 127.0.0.1:5090). Scripturile: `deploy/pregateste-productie.ps1`, `porneste-productie.ps1`, `opreste-productie.ps1`; binarele, certificatele token-urilor și secretele stau în `productie/` (ignorat de git). | Decizia clientului: fără cost de hosting, datele rămân la firmă. Aplicația web și API-ul pe aceeași origine (D-19). | În Production: fără autentificarea de test prin headere, fără date demo, fără OpenAPI; doar numele de gazdă configurat; limitare de încercări la login pe IP (`Securitate:IncercariAutentificarePeMinut`); X-Forwarded-* acceptate doar de la proxy-ul local. Disponibilitatea depinde de calculator și de conexiunea firmei; PostgreSQL NU se expune. Adresele de întoarcere ale clientului OAuth se cumulează (dezvoltarea și producția folosesc aceeași bază). |
| D-25 | **PDF-urile documentelor: formatul standard randat direct cu PDFsharp-MigraDoc 6.2.4 (MIT)**, descris prin date (`AspectDocument`: antet, tabel, totaluri, semnături); șablonul Word al firmei pentru tipul de formular are prioritate (Open XML + Gotenberg, D-09 / D-10) prin `IServiciuDocumente`. Completează D-10. | Gotenberg / LibreOffice nu rulează încă la client; documentele trebuie tipărite de acum. | PDFsharp rămâne fixat pe 6.2.x: de la versiunile noi pachetul e AGPL-3.0. Fonturile: Arial (Windows) sau DejaVu Sans (Linux, `fonts-dejavu-core`). `System.Security.Cryptography.Pkcs` fixat explicit pe versiunea corectată (PDFsharp aduce 8.0.1, cu vulnerabilități). |
| D-26 | **Producția fără reverse proxy (înlocuiește partea Caddy / Let's Encrypt din D-24):** API-ul servește și aplicația web (`Web:Radacina`), ascultă direct pe `https://0.0.0.0:<port>` (Kestrel) cu un certificat autosemnat generat de `deploy/pregateste-productie.ps1` pentru domeniu + IP-urile din rețea; fără emitent OIDC fix (emitentul = adresa folosită), ca aplicația să meargă și pe domeniu, și pe IP-ul din rețea. | Clientul vrea doar portul redirecționat, fără dependențe externe; portul 80 public rămâne al routerului, deci Let's Encrypt nu putea verifica domeniul. HTTPS rămâne obligatoriu (criptografia din browser pentru PKCE și parolele în clar). | Browserul cere o confirmare a certificatului la prima vizită; un certificat de la o autoritate se poate pune oricând în `Kestrel:Endpoints:Https:Certificate`. Firewall-ul Windows trebuie deschis pentru port (regula se creează doar cu drepturi de administrator). |
| D-27 | **Centrul de import („Import documente”, în aplicație, nu o aplicație separată):** un fișier cu mai multe documente se citește o dată, `ImpartireDocumente` (logică pură, SharedKernel) propune documentele (paginile consecutive de același tip, despărțite când se schimbă numărul sau data; e-Factura și factura tipărită cu același număr = un document; avizul și certificatele la ultima factură), utilizatorul corectează (tip, unire, despărțire), iar fiecare document se taie într-un PDF separat (PDFsharp) și se importă prin ecranul tipului lui. OCR-ul se ține în cache pe pagină; textul paginilor trece în PDF-ul tăiat. În PDF-urile combinate doar paginile fără text trec prin OCR. | Pe hârtie, oamenii scanează împreună mai multe achiziții, necesare și bonuri. O aplicație separată ar fi dublat autentificarea, drepturile și accesul la bază. | Importul fiecărui document rămâne cel existent (aceleași verificări, același original arhivat: doar paginile lui). Pagina cere `aprovizionare.creare` sau `financiar.creare` (`CereOricarePermisiune`); fiecare import își cere dreptul lui. Fișierul citit stă 30 min în memoria serverului (după firmă + SHA-256). Bonurile de consum se recunosc, dar se introduc încă manual în Stocuri. Limita: 40 de pagini (`Ocr:PaginiMaxime`). |
| D-28 | **Aplicația de test a importului (`tools/ErpConstructii.TestImport`), separată de aplicație:** citește toate fișierele din `Sabloane/` cu exact codul aplicației (extractori → clasificare → împărțire → interpretor; `CitireFacturaText` e comună cu importul facturilor) și compară cu valorile confirmate în `Sabloane/_asteptat/<fișier>.json`, verificate de om pe imaginea paginilor. Raport HTML (`Sabloane/_rezultate/raport.html`): paginile lângă ce s-a citit, diferențele în roșu. Textul extras se păstrează pe disc (după SHA-256), deci o rulare după o schimbare a interpretorilor durează secunde. | Corecturile făcute pe un singur document stricau altele fără să se vadă („ne învârtim în cerc”). | Orice schimbare a unui interpretor se rulează pe toate documentele (cod de ieșire 1 la diferențe). Un document nou: se pune în `Sabloane/`, se rulează, se verifică raportul, `--confirma <nume>`, apoi se corectează în JSON valorile citite greșit (devin defecte de rezolvat). Fișierele și valorile confirmate rămân în afara git-ului (date reale). |
| D-29 | **Aplicația Windows de import documente (WPF, `clients/desktop/ErpConstructii.ImportDesktop`), auxiliară:** lucrează exclusiv prin API-ul aplicației principale (endpoint-urile centrului de import și ale fiecărui tip de document), nu direct în bază. Login OAuth pentru aplicații native (RFC 8252): Authorization Code + PKCE prin browserul sistemului, întoarcere pe `http://127.0.0.1:47615-47617/callback/`, client public `erp-import`. Pornire din web prin schema `erp-import://` (înregistrată în HKCU la pornire) sau direct; distribuită ca un singur .exe din aplicația web (`/descarcari/ErpImport.exe`, publicat de `pregateste-productie.ps1`). | Clientul vrea o aplicație de sine stătătoare pentru importul fișierelor cu multe documente, cu verificare pe rând lângă pagini. Prin API: aceleași drepturi (regula 4), aceeași RLS pe firmă, același audit, aceleași potriviri și verificări ca în web; nimic duplicat. | Merge doar cu serverul instalat și pornit. Certificatul autosemnat se acceptă o dată, după amprentă (TOFU). Bonurile de consum doar se recunosc (fără interpretor încă). Pagina web „Import documente” rămâne (aceleași funcții, pentru cine nu are Windows). |
| D-30 | **Importul bonurilor de consum de pe hârtie (GC-087, câte două pe pagină):** paginile se recunosc după codul formularului / coloanele predator–primitor–eliberată, bonurile se separă după rândul „UNITATEA” (`ZoneDocumente`, SharedKernel; `DocumentDetectat.Zona`), `InterpretorBonConsum` (Stocuri) citește numărul, data, liniile (valorile asociate coloanei după capătul din dreapta, aliniate la dreapta). Importul nu creează un document nou: pentru fiecare linie se alege materialul din **stocul șantierului** proiectului (propus după denumire / alias / asemănare) și, opțional, articolul de deviz, apoi bonul se emite prin consumul obișnuit, la CMP. | Bonurile de pe hârtie descriu ieșiri din gestiune: în aplicație consumul trebuie să scadă stocul real, la costul lui, nu la prețul din vechiul program. | Materialul trebuie să fie deja în stocul șantierului (NIR + transfer), altfel serverul refuză („stoc insuficient”). Prețul / valoarea din bon sunt doar informative. Numărul de pe hârtie, primitorul și lucrarea merg în observații; începutul lor („Bon de consum nr. X din Z (import)”) recunoaște bonul deja importat. Originalul nu se arhivează încă (Stocuri nu are arhivă de documente). Importul e în aplicația Windows; pagina web doar recunoaște bonurile. |
| D-31 | **Recepția parțială a facturilor: mai multe NIR-uri pe o factură** (înlocuiește „o singură recepție pe factură” din D-23). Fiecare NIR cuprinde liniile și cantitățile sosite; o linie marcată „restul vine” (`LinieNir.Partiala`) rămâne deschisă, una nemarcată se închide (lipsa definitivă / surplusul cer observație). Starea liniilor: `StareReceptie` (Stocuri, pur). **Consumul unei facturi întregi:** bonul de consum se completează cu materialele recepționate ale facturii; ce nu e încă în șantier se transferă întâi din depozitul recepției (bon de transfer). | Marfa vine des în tranșe; gestionarul trebuie să poată recepționa ce a sosit fără să închidă factura. Materialele cumpărate pentru un șantier se consumă de obicei toate. | NIR-urile vechi (cu toată factura) își păstrează sensul: liniile lor sunt închise. Valoarea intrată în stoc se calculează pe fiecare NIR (cantitate × preț), deci poate diferi cu bani de valoarea liniei din factură când prețul afișat e rotunjit. Transferul și consumul rămân documente separate (BT + BC), cum cere evidența. |
| D-32 | **Trasabilitatea stocului (proveniența pe NIR / factură) se calculează din mișcări, cu ieșirile atribuite FIFO** (`TrasabilitateStoc`, Stocuri, pur): ce e acum într-o gestiune provine din cele mai recente intrări; transferul (în șantier sau retur) mută loturile cu originea lor; stornarea unui NIR scoate exact cantitatea acelui NIR; plusul de inventar e o origine proprie. Raportul `GET /api/stocuri/trasabilitate` (Recepții → „Proveniență materiale”), cu export CSV. Evaluarea rămâne CMP (D-23). | Clientul vrea să știe pe ce factură și NIR au intrat materialele din depozit, fără să schimbe evaluarea și fără ca gestionarul să aleagă loturi la fiecare ieșire. | Atribuirea e o convenție (FIFO), nu loturi fizice: dacă e nevoie de loturi reale (ex. certificate de conformitate pe lot, alegerea lotului la transfer), se adaugă lotul pe liniile transferului / consumului. Valoarea din raport e la prețul de intrare, deci diferă de valoarea CMP din evidență. Calculul parcurge toate mișcările firmei (filtrul pe material le reduce). |
